01 · Abstract 01 · 摘要（Abstract）

The Short Version

核心结论速览

We hardened clean-session-curate, an open-source skill for exporting anonymized coding-agent logs, using a deterministic AST scrubber and an adversarial evaluation loop. Even after driving synthetic fragment leaks from 51/55 down to 0/63 and passing 23/23 unit tests, a fresh blind LLM attacker rated two unseen holdout sets as Critical re-identification risk—driven by plain-English and Chinese prose (advisor names, a 17-person org roster, street addresses, unpublished paper titles, and one-time passcodes) that regex cannot reliably detect.

We rebuilt the skill into a 4-Pass Hybrid Pipeline: deterministic AST scrubbing, a sharded multi-agent Privacy Hunter (max(20%, 20 KB) shards with 10% overlap plus a Merger agent), deterministic AST literal redaction with ASCII word-boundary guards, and a fresh blind Verifier gate. After freezing the skill at commit b80590d (26/26 tests) and testing it one-shot on a strictly uncontaminated 5.76 MB Holdout #3 (10 unseen Claude and Codex sessions across 6 disjoint projects), both blind verifiers returned a first-shot PASS (0 Critical, 0 High, 0 Medium leaks, utility intact, 10/10 raw SHA-256 unchanged).

围绕开源编程智能体会话脱敏技能 clean-session-curate，我们构建了一套对抗式评测与加固流程。实测发现：即便确定性 AST 清洗器已将合成敏感片段泄漏从 51/55 压降至 0/63 并通过全部 23/23 单元测试，无先验记忆的盲测攻击智能体仍在两组未见过的 Holdout 集上给出了 Critical（极高危重识别风险）——根源在于中英文自然语言正文中的导师与参与者姓名、17 人中文组织花名册及单姓简称、物理街道地址、未发表论文标题与一次性验证码，这些语义级隐私是正则表达式无法穷举的。

为此，我们将技能重构为四阶段混合流水线：Pass 1 确定性 AST 清扫 → Pass 2 分片多智能体隐私猎手（按 max(20%, 20 KB) 切分并保留 10% 边界重叠，配 1 个归并智能体）→ Pass 3 带 ASCII 词边界守卫的 AST 词表精确替换 → Pass 4 全新盲测验收门禁。在将技能冻结于提交 b80590d（26/26 测试通过）后，我们在严格零污染的 5.76 MB Holdout #3（来自 6 个全新项目的 10 条 Claude Code 与 Codex 会话）上一次性实测，两组盲测验收官均给出首轮 PASS（0 严重 / 0 高危 / 0 中危泄漏、任务效用完好、10/10 原始文件 SHA-256 零改动）。

02 · Motivation 02 · 背景动机（Motivation）

Why Regex Scrubbing Fails on Real Agent Logs

为什么纯正则清洗在真实智能体日志面前必然失效

Sharing coding-agent transcripts for research, debugging, or postmortems is much harder than scrubbing ordinary server logs. A single Claude Code or Codex .jsonl trace mixes shell commands, JSON-encoded tool arguments, git status output, browser accessibility dumps, email snippets, and multi-turn conversation—often across several megabytes.

When we audited the baseline clean-session-curate workflow against real OpenCode v2, pi, Claude Code, and Codex sessions, three distinct failure modes surfaced immediately:

  1. Silent discovery and structural bypasses. Baseline discovery found 0/3 OpenCode v2 sessions because OpenCode had removed the opencode db CLI command the script relied on. Worse, the underlying Capsule 1.0.0 path masker skipped JSON arrays and Codex session_meta / response_item payloads—leaving 51/55 synthetic leak fragments exposed (92.7%) and causing an offline pre-API secret gate to block 27/28 real local sessions.
  2. Regex collisions corrupting useful prose. Naive secret fixes backfired immediately: an unanchored sk- API-key pattern turned task-notification and risk-assessment into ta[REDACTED] and ri[REDACTED] across 9/10 local traces, while a generic path masker rewrote #!/usr/bin/env node into a synthetic project path.
  3. The regex ceiling on natural-language PII. Even after we fixed every structural bug, anchored secret patterns, added read-only SQLite discovery (mode=ro&immutable=1 so WAL/SHM files never mutate), and passed 23/23 unit tests, a fresh blind LLM attacker broke both unseen holdout sets in minutes.

在科研评测、团队复盘或训练语料沉淀中分享编程智能体会话，难度远高于普通后端日志脱敏。单份 Claude Code 或 Codex 的 .jsonl 会话动辄数 MB，内部交织着终端命令、JSON 字符串化的工具入参、Git 状态记录、浏览器无障碍树快照、邮件片段与多轮自由对话。

当我们对 OpenCode v2、pi、Claude Code 与 Codex 的真实会话审计基线版 clean-session-curate 时，三类致命缺陷立刻浮出水面：

  1. 静默发现失效与结构级绕过。 OpenCode v2 移除了旧版依赖的 opencode db 子命令，导致基线发现率为 0/3 且无任何报错；更严重的是，底层依赖的 Capsule 1.0.0 路径脱敏函数不递归 JSON 数组，也不识别 Codex 的 session_meta / response_item 结构，导致 51/55 个合成敏感片段直接漏网（92.7%），本地离线密钥门禁更是拦截了 27/28 条真实会话。
  2. 正则误伤破坏正常技术文本。 简单粗暴地补正则会立刻破坏语料可用性：未加词边界锚定的 sk- 规则把 9/10 条会话里的英文词 task-notification 和 risk-assessment 截断成了 ta[REDACTED] 与 ri[REDACTED]；宽泛路径规则甚至把脚本头 #!/usr/bin/env node 改写成了假路径。
  3. 纯正则无法逾越的自然语言 PII 天花板。 即便我们修复了全部结构漏洞、使用 mode=ro&immutable=1 锁死 SQLite 只读访问（保证 WAL/SHM 零改动）并通过了 23/23 项单元测试，盲测攻击智能体依然在几分钟内攻破了两组未见过的 Holdout 测试集。

No amount of regex tuning can tell a workshop participant's first name from a code identifier, or a street address from a test fixture. Conversely, asking an LLM to hand-edit a 5 MB JSONL file fails in the opposite direction: models truncate long logs, break JSON escaping, and miss scattered occurrences.

无论怎么调正则表达式，代码都不可能区分“参会者的英文名”与“普通变量名”，也无法预知哪一句中文是真实办公地址；反过来，如果直接让大模型手改 5 MB 的 JSONL 原文，又会引发长文本截断、JSON 转义损坏与同词漏改。

03 · Method 03 · 核心方法（Method）

The 4-Pass Hybrid Multi-Agent Pipeline

四阶段混合分片多智能体流水线

Because clean-session-curate is an agent skill, we stopped treating it like a standalone regex CLI. Instead, we drew a clean boundary: deterministic code owns every file write and AST walk, while read-only agents own semantic discovery and adversarial verification.

既然 clean-session-curate 本身就是一个智能体技能（Agent Skill），就不该把它当成死板的纯正则脚本。我们划定了清晰的职责边界：确定性代码独占所有文件读写与 AST 语法树遍历，而只读子智能体专职负责语义级隐私发现与对抗式盲测验收。

Three Design Decisions That Actually Moved the Needle

真正决定成败的三项工程设计

  • Sharding Pass 2 into max(20%, 20 KB) slices with 10% overlap. In our first hybrid prototype (Holdout A1 & A2), a single Privacy Hunter scanning megabytes of JSONL missed subtle clues buried in noise—forcing 2 to 4 retry loops with the Blind Verifier. Our chunker (scripts/chunk_for_hunter.mjs) slices the Pass-1 corpus into bounded overlapping shards (including splitting giant single JSONL lines) so every parallel Hunter keeps sharp attention and no entity spanning a boundary is lost. One Merger agent then deduplicates overlapping terms and propagates cross-shard shorthands.
  • ASCII alphanumeric boundary guards on --terms. When an agent flags a short identifier like PSU or Erie, naive substring replacement silently corrupts capsule and experience. In anonymize_session.mjs, any --terms literal starting or ending with [A-Za-z0-9] is automatically wrapped in (?<![A-Za-z0-9])...(?![A-Za-z0-9]), while CJK strings still match cleanly inside unspaced Chinese sentences.
  • A fresh blind verifier as a hard packaging gate. Pass 4 spawns a brand-new read-only verifier with zero memory of Passes 1–3. Once loud leaks (full names, rosters, tokens) are gone, second-order clues that were invisible in noise—like a single Chinese surname or a regex bucket alternation—stand out immediately.
  • Pass 2 按 max(20%, 20 KB) 分片并保留 10% 边界重叠。 在早期单猎手原型（Holdout A1 与 A2）中，单个智能体面对数 MB 日志容易注意力稀释，遗漏淹没在噪声里的细微线索，导致需要与盲测门禁往返 2～4 轮才能收敛。新增的 scripts/chunk_for_hunter.mjs 将语料切分为有界重叠分片（超长单行 JSONL 也会自动重叠切片），让每个并行 Hunter 保持高召回率且不丢跨边界实体，最后由 1 个 Merger 智能体统一去重并跨片补全简称。
  • --terms 的 ASCII 字母数字边界守卫。 当智能体提取出 PSU 或 Erie 这类短缩写时，裸子串替换会把正常英文词 capsule 和 experience 破坏掉。我们在 anonymize_session.mjs 中对首尾为 [A-Za-z0-9] 的词条自动包裹 (?<![A-Za-z0-9])...(?![A-Za-z0-9]) 边界守卫，同时让中文词条在无空格的中文句子里保持精准匹配。
  • 以“零先验盲测验收”作为打包硬门禁。 Pass 4 启动一个对前序步骤毫无记忆的全新只读智能体。当显眼的大块隐私（全名、花名册、长密钥）被清干净后，原本藏在噪声里的二阶线索——如中文单姓简称或正则桶名前缀——会立刻暴露在盲测视野中。
04 · Results 04 · 实测结果（Results）

Empirical Progression and an Uncontaminated Holdout Check

多轮演进数据与严格零污染 Holdout 终测

A common trap in adversarial engineering is accidentally turning your holdout set into a second dev set. We fell into that trap honestly—and caught it before claiming victory.

对抗式工程中最容易踩的陷阱，就是在根据测试集报错修完代码后，不知不觉把 Holdout 测试集变成了“第二开发集”。我们坦诚识别出了这一风险，并在宣布成功前补上了真正的零污染终测。

Why We Built Holdout #3 (Zero-Contamination Protocol)
Once we inspected Holdout A1 and A2 failures to add deterministic rules (session-owner, provider user-/thread_ IDs, commit: short SHAs) and Hunter checklist hints, A1 and A2 were no longer untouched blind tests. To prove the architecture generalizes without overfitting, we froze the skill at commit b80590d (26/26 tests) before sampling Holdout #3 from 6 completely disjoint local projects—and ran it one-shot with zero edits allowed.
为什么要专门构建 Holdout #3（严格零污染协议）

On the strictly uncontaminated 5.76 MB Holdout #3 corpus, sharding changed the game. Six parallel Hunter agents inspected 1.15 MB shards with 115 KB overlap and caught 22 student names, 18 handles, 6 partially masked phone numbers, an IP-bearing sslip.io hostname, a shared artifact URL, and private repo names—all on Pass 2. The Merger agent deduplicated 222 raw candidates into 180 clean terms, Pass 3 applied them with zero JSON corruption, and both fresh blind verifiers passed on Loop 1. Only minor Low-severity residue remained (opaque API req_ IDs, coarse timezone labels, a typo-glued RFC1918 LAN IP, and a 2-character UI truncation).

在严格零污染的 5.76 MB Holdout #3 语料上，分片并行机制彻底改变了战局：6 个并行 Hunter 智能体各自深挖 1.15 MB 分片（含 115 KB 重叠区），在 Pass 2 一次性揪出了 22 个中文学生真名、18 个昵称/账号、6 个半遮蔽手机号、内嵌公网 IP 的 sslip.io 域名、分享链接及全部私有仓库名。Merger 智能体将 222 条候选词去重整合为 180 条词表，Pass 3 零损坏完成 AST 替换，最终两组盲测验收智能体在第 1 轮（Loop 1）即一次性给出 PASS——仅剩少量不影响隐私安全的低风险项（不透明 API req_ 请求号、粗粒度时区缩写、一处紧贴英文词的内网保留 IP 以及 2 字符 UI 截断前缀）。

05 · Honest Limits 05 · 已知边界（Honest Limits）

Where This Architecture Still Has Boundaries

当前架构仍需注意的三条工程边界

The skill is ready for daily real-world use, and far safer than deterministic scrubbing alone—but three concrete limits remain worth engineering before a broad upstream release:

该技能已具备日常生产可用性，安全性远超传统纯正则方案；但在更大规模推广前，仍有三处边界值得坦诚说明：

LIMIT 01 · SCALING
边界 01 · 超大语料上限

Giant Exports (>15 MB) Need a Ceiling

超大导出包（>15 MB）需加分片上限

max(20%, 20 KB) worked cleanly at 5.76 MB (~1.15 MB/shard), but on a 30 MB export, 20% would yield 6 MB shards. Capping shard size at 500 KB keeps Hunter recall high at any scale.

max(20%, 20 KB) 在 5.76 MB 语料上（约 1.15 MB/片）表现极佳，但若遇到 30 MB 导出包，20% 会产生 6 MB 大分片。后续加上 500 KB 硬上限即可适配任意体量。

LIMIT 02 · VERIFIER
边界 02 · 门禁自动分片

Shard Pass 4 Automatically Too

Pass 4 盲测门禁同样应当自动分片

On Holdout #3 we manually split Pass 4 into two verifiers (Claude and Codex) to keep review depth sharp. SKILL.md should reuse chunk_for_hunter.mjs for Pass 4 whenever exports exceed ~1 MB.

在 Holdout #3 评测中，我们将 Pass 4 按 Claude 与 Codex 拆成两个盲测官以保证审查深度；下一步可在语料超过 1 MB 时直接复用 chunk_for_hunter.mjs 自动分片验收。

LIMIT 03 · PORTABILITY
边界 03 · 宿主与跨平台验证

Host-Agent & Windows CI

宿主子智能体能力与 Windows CI

Pass 1 is pure Node.js 20+ and runs anywhere, but Passes 2 and 4 rely on a host agent that supports subagents (or sequential shard loops). All runs were verified on macOS; Windows CI is still pending.

Pass 1 为纯 Node.js 20+ 脚本可随处运行，但 Pass 2 与 Pass 4 依赖宿主支持只读子智能体（或按分片顺序串行审阅）。本文实验均在 macOS 完成，Windows CI 仍待补齐。

Portable Takeaway
可迁移的工程启示

If you are building privacy tooling inside an agent workflow, don't force regex to understand human prose, and don't let an LLM hand-edit raw logs. Let deterministic code own the AST and file I/O, shard semantic hunting into bounded overlapping chunks so no agent loses focus, and require a fresh blind verifier to sign off before anything gets zipped.
